# .NET Core Domain  Driven Design

**Domain-Driven Design (DDD)** is a software development approach that focuses on creating a model of the problem domain that is central to the application, and structuring the software to reflect that model. In **DDD**, you design and build software systems by focusing on the **core domain**, leveraging business logic, and breaking down the system into smaller, meaningful components like **Entities**, **Value Objects**, **Aggregates**, **Repositories**, and **Services**.

Let’s walk through **DDD concepts** with an example in **.NET Core**, focusing on the main building blocks:

### 1. Entities

- An **Entity** is an object that is defined by its unique identity (ID) rather than its attributes. Its lifecycle is important, and it often changes state.

- Example: A Customer in an e-commerce application is an entity because it has an identity (CustomerId) that is unique, and its state changes over time (e.g., address, name, orders).

```csharp
public class Customer
{
public Guid CustomerId { get; private set; }
public string Name { get; private set; }
public string Email { get; private set; }
public Address Address { get; private set; }
public Customer(string name, string email, Address address)
{
CustomerId = Guid.NewGuid();
Name = name;
Email = email;
Address = address;
}
public void UpdateAddress(Address newAddress)
{
Address = newAddress;
}
}
```

### 2. Value Objects

- A **Value Object** is an immutable type that has no identity. It is defined by its attributes and typically represents a concept like **Address** or **Money**.

- Example: Address can be a value object since it doesn’t have a unique identity but represents an address with fields like street, city, etc.

```csharp
public class Address
{
public string Street { get; private set; }
public string City { get; private set; }
public string ZipCode { get; private set; }
public Address(string street, string city, string zipCode)
{
Street = street;
City = city;
ZipCode = zipCode;
}
```

// Two addresses are considered equal if all attributes are the same.

public override bool Equals(object obj)

```csharp
{
if (obj is Address address)
{
return Street == address.Street && City == address.City && ZipCode == address.ZipCode;
}
return false;
}
public override int GetHashCode() => (Street, City, ZipCode).GetHashCode();
}
```

### 3. Aggregates

- An **Aggregate** is a cluster of entities and value objects that are treated as a single unit for data changes. The **Aggregate Root** is the main entity that controls access to the rest of the aggregate.

- Example: A Order is an aggregate root. It contains OrderItems (Entities) and uses the Customer entity to associate with the user who placed the order.

```csharp
public class Order
{
public Guid OrderId { get; private set; }
public Customer Customer { get; private set; }
public List<OrderItem> OrderItems { get; private set; }
public decimal TotalAmount => OrderItems.Sum(item => item.Price * item.Quantity);
public Order(Customer customer)
{
OrderId = Guid.NewGuid();
Customer = customer;
OrderItems = new List<OrderItem>();
}
public void AddItem(OrderItem item)
{
OrderItems.Add(item);
}
public void RemoveItem(OrderItem item)
{
OrderItems.Remove(item);
}
}
```

### OrderItem

```csharp
public class OrderItem
{
public Guid ProductId { get; private set; }
public string ProductName { get; private set; }
public int Quantity { get; private set; }
public decimal Price { get; private set; }
public OrderItem(Guid productId, string productName, int quantity, decimal price)
{
ProductId = productId;
ProductName = productName;
Quantity = quantity;
Price = price;
}
}
```

### 4. Repositories

- A **Repository** is a pattern used to **abstract data access** and handle the persistence of aggregates. Repositories ensure that domain entities stay isolated from data access concerns.

- Example: The OrderRepository is responsible for retrieving and saving Order aggregates.

```csharp
public interface IOrderRepository
{
Order GetOrderById(Guid orderId);
void AddOrder(Order order);
void SaveChanges();
}
public class OrderRepository : IOrderRepository
{
private readonly DbContext _context;
public OrderRepository(DbContext context)
{
_context = context;
}
public Order GetOrderById(Guid orderId)
{
return _context.Orders.Include(o => o.OrderItems).FirstOrDefault(o => o.OrderId == orderId);
}
public void AddOrder(Order order)
{
_context.Orders.Add(order);
}
public void SaveChanges()
{
_context.SaveChanges();
}
}
```

### 5. Domain Services

- **Domain Services** contain domain logic that doesn’t naturally belong in an entity or value object. They perform operations involving multiple entities or aggregates.

- Example: A service to calculate a discount based on the total order amount.

```csharp
public class DiscountService
{
public decimal CalculateDiscount(Order order)
{
if (order.TotalAmount > 1000)
return order.TotalAmount * 0.1m; // 10% discount for orders over 1000
return 0;
}
}
```

### 6. Application Services

- **Application Services** act as the entry point to the domain logic. They handle use cases and orchestrate the interaction between aggregates and repositories.

- Example: OrderService that handles creating new orders, adding items to an order, and processing payments.

```csharp
public class OrderService
{
private readonly IOrderRepository _orderRepository;
private readonly DiscountService _discountService;
public OrderService(IOrderRepository orderRepository, DiscountService discountService)
{
_orderRepository = orderRepository;
_discountService = discountService;
}
public void CreateNewOrder(Customer customer)
{
var order = new Order(customer);
_orderRepository.AddOrder(order);
_orderRepository.SaveChanges();
}
public void AddItemToOrder(Guid orderId, OrderItem orderItem)
{
var order = _orderRepository.GetOrderById(orderId);
order.AddItem(orderItem);
_orderRepository.SaveChanges();
}
public decimal GetOrderDiscount(Guid orderId)
{
var order = _orderRepository.GetOrderById(orderId);
return _discountService.CalculateDiscount(order);
}
}
```

### 7. Domain Events (Optional)

- **Domain Events** capture occurrences in the domain that might need to trigger actions or be processed asynchronously. In DDD, they help to decouple different parts of the system.

- Example: When an order is placed, an OrderPlacedEvent might be raised to notify other parts of the system.

```csharp
public class OrderPlacedEvent
{
public Order Order { get; }
public OrderPlacedEvent(Order order)
{

}
```

### 8. Context and Bounded Context

- In DDD, the concept of **bounded context** refers to defining a boundary within which a particular domain model applies. For example, the ordering system (customer, order, products) is a bounded context, separate from a shipping or inventory context.

### Example Scenario in .NET Core

- The **Order Aggregate** contains multiple OrderItem entities.

- The **OrderService** orchestrates operations like creating an order or adding items.

- The **OrderRepository** handles persisting and retrieving orders from a database.

- A **DiscountService** applies business rules for calculating discounts.

- **Domain Events** can be used to notify other parts of the system when a key event (like placing an order) occurs.

### Conclusion

Domain-Driven Design (DDD) helps to break down complex business domains by focusing on the **core business logic** and ensuring that the code structure reflects the **domain model**. In .NET Core, DDD principles can be implemented using familiar constructs such as **Entities**, **Value Objects**, **Aggregates**, **Repositories**, and **Domain Services**, while maintaining clear boundaries between application and infrastructure layers.

**Domain-Driven Design (DDD)** with **Domain Events** is an advanced pattern where important changes in the domain model trigger events that can be handled either synchronously or asynchronously. **Domain Events** allow decoupling between different parts of the system, making the code more modular, maintainable, and scalable.

## What Are Domain Events?

A **Domain Event** is something that happens in the domain that might be of interest to other parts of the system. The key idea is to decouple different behaviors so that when something significant happens in the domain, other parts of the system can react to it without tight coupling.

For example, in an e-commerce application, when an Order is placed, the system might trigger events such as OrderPlacedEvent that other components (like inventory, billing, and shipping) listen to and handle.

### Steps to Implement Domain Events in .NET Core

1.  **Define the Domain Event**

2.  **Raise Domain Events in the Aggregate**

3.  **Create Handlers for Domain Events**

4.  **Dispatch Domain Events**

Let’s walk through a practical **.NET Core** example to understand how **DDD** works with **Domain Events**.

### Scenario

In an e-commerce application, when a customer places an order, an event (OrderPlacedEvent) is raised. The system responds by adjusting inventory and sending a notification email to the customer.

### Step 1: Define the Domain Event

A **Domain Event** should be immutable and contain the information needed for handlers to act upon it.

```csharp
public class OrderPlacedEvent
{
public Guid OrderId { get; }
public Guid CustomerId { get; }
public DateTime OrderDate { get; }
public OrderPlacedEvent(Guid orderId, Guid customerId, DateTime orderDate)
{
OrderId = orderId;
CustomerId = customerId;
OrderDate = orderDate;
}
}
```

This event captures the necessary data when an order is placed.

### Step 2: Raise Domain Events in the Aggregate

You should raise domain events within your aggregates when certain actions happen, like placing an order.

```csharp
public class Order
{
public Guid OrderId { get; private set; }
public Guid CustomerId { get; private set; }
public List<OrderItem> OrderItems { get; private set; }
public DateTime OrderDate { get; private set; }
private List<object> _domainEvents = new List<object>();
public IReadOnlyList<object> DomainEvents => _domainEvents;
public Order(Guid customerId)
{
OrderId = Guid.NewGuid();
CustomerId = customerId;
OrderDate = DateTime.Now;
OrderItems = new List<OrderItem>();
}
public void AddItem(OrderItem item)
{
OrderItems.Add(item);
}
public void PlaceOrder()
{
// Add the logic to place the order
// Raise the OrderPlacedEvent
var orderPlacedEvent = new OrderPlacedEvent(OrderId, CustomerId, OrderDate);
_domainEvents.Add(orderPlacedEvent);
}
public void ClearDomainEvents()
{
_domainEvents.Clear();
}
}
```

In this example, when the PlaceOrder method is called, it raises an OrderPlacedEvent which is stored in a collection of domain events (_domainEvents).

### Step 3: Create Handlers for Domain Events

Now that we are raising the domain event, we need to create handlers that will react to these events.

Let’s create a couple of handlers:

1.  **InventoryHandler** – Updates the inventory.

2.  **EmailNotificationHandler** – Sends a notification email to the customer.

```csharp
public class InventoryHandler
{
public void Handle(OrderPlacedEvent domainEvent)
{
Console.WriteLine($"Adjusting inventory for Order ID: {domainEvent.OrderId}");
// Implement inventory adjustment logic
}
}
public class EmailNotificationHandler
{
public void Handle(OrderPlacedEvent domainEvent)
{
Console.WriteLine($"Sending notification to Customer ID: {domainEvent.CustomerId}");
// Implement email notification logic
}
}
```

Each handler reacts to the event and performs some side effect (updating the inventory or sending a notification).

### Step 4: Dispatch Domain Events

Now we need a **Domain Event Dispatcher** that can be responsible for dispatching events to their appropriate handlers.

```csharp
public class DomainEventDispatcher
{
private readonly IEnumerable<object> _handlers;
public DomainEventDispatcher(IEnumerable<object> handlers)
{
_handlers = handlers;
}
public void Dispatch(object domainEvent)
{
foreach (var handler in _handlers)
{
var handlerType = handler.GetType();
var eventType = domainEvent.GetType();
var method = handlerType.GetMethod("Handle", new[] { eventType });
if (method != null)
{
method.Invoke(handler, new[] { domainEvent });
}
}
}
}
```

The DomainEventDispatcher looks for all handlers that match the domain event and invokes their Handle method.

### Step 5: Putting It All Together in the Application Layer

1.  **Raising Domain Events**: When the PlaceOrder method is called on the Order entity, it raises the OrderPlacedEvent.

2.  **Dispatching Domain Events**: After placing the order, we call the dispatcher to handle the events.

```csharp
public class OrderService
{
private readonly IOrderRepository _orderRepository;
private readonly DomainEventDispatcher _domainEventDispatcher;
public OrderService(IOrderRepository orderRepository, DomainEventDispatcher domainEventDispatcher)
{
_orderRepository = orderRepository;
_domainEventDispatcher = domainEventDispatcher;
}
public void PlaceOrder(Order order)
{
// Place the order
order.PlaceOrder();
_orderRepository.Save(order);
// Dispatch all the domain events
foreach (var domainEvent in order.DomainEvents)
{
_domainEventDispatcher.Dispatch(domainEvent);
}
// Clear the events after dispatching them
order.ClearDomainEvents();
}
}
```

### Step 6: Dependency Injection and Startup Configuration

Finally, you need to register the domain event handlers and the dispatcher in the **Startup.cs** or in your dependency injection framework.

```csharp
public void ConfigureServices(IServiceCollection services)
{
// Register the handlers
services.AddScoped<InventoryHandler>();
services.AddScoped<EmailNotificationHandler>();
// Register the dispatcher with handlers
services.AddScoped<DomainEventDispatcher>(provider =>
{
var handlers = new List<object>
{
provider.GetService<InventoryHandler>(),
provider.GetService<EmailNotificationHandler>()
};
return new DomainEventDispatcher(handlers);
});
// Other services
}
```

### Full Example Workflow

1.  A customer places an order using the OrderService.

2.  The PlaceOrder method in the Order aggregate raises an OrderPlacedEvent.

3.  The DomainEventDispatcher finds the appropriate event handlers (InventoryHandler and EmailNotificationHandler).

4.  Each handler processes the event:

    - **InventoryHandler** adjusts the inventory.

    - **EmailNotificationHandler** sends a notification to the customer.

5.  The events are cleared from the aggregate once handled.

### Conclusion

Using **Domain Events** in **DDD** allows for loose coupling between different parts of the system. It enables a more modular design where domain logic is kept clean and additional responsibilities (like sending emails or adjusting inventory) are handled by separate event handlers. This pattern is powerful when dealing with complex domains and can be easily implemented in **.NET Core** using services and dependency injection.

Implementing **Domain-Driven Design (DDD)** with **Domain Events** and **CQRS (Command Query Responsibility Segregation)** in **.NET Core** is a powerful architectural pattern that decouples the **write** and **read** models while enabling scalable, maintainable code. Here, we’ll go through an example that combines **DDD**, **Domain Events**, and **CQRS** in a **.NET Core** application.

### Key Concepts

1.  **DDD (Domain-Driven Design)**: Focuses on the core business domain, breaking down complex systems into aggregates, entities, and value objects.

2.  **Domain Events**: Represent significant events that occur in the domain, enabling decoupling by notifying other parts of the system.

3.  **CQRS (Command Query Responsibility Segregation)**: Separates the **write** model (commands) from the **read** model (queries) for better scalability and performance.

4.  **Event Sourcing** (optional): Instead of storing the current state of an object, it stores a sequence of events that led to the current state.

### Scenario

In an e-commerce application, when a customer places an order, the system performs the following:

1.  Places the order (write model).

2.  Triggers a domain event (OrderPlacedEvent).

3.  Handles the event by updating inventory and notifying the customer.

4.  Separates **reads** and **writes** using **CQRS**.

### Step-by-Step Example of DDD + Domain Events + CQRS in .NET Core

### Step 1: Define the Domain Model (Aggregates and Entities)

Let’s start by defining an **Order Aggregate** in our domain model.

```csharp
public class Order
{
public Guid OrderId { get; private set; }
public Guid CustomerId { get; private set; }
public DateTime OrderDate { get; private set; }
public List<OrderItem> OrderItems { get; private set; }
private List<object> _domainEvents = new List<object>();
public IReadOnlyList<object> DomainEvents => _domainEvents;
public Order(Guid customerId)
{
OrderId = Guid.NewGuid();
CustomerId = customerId;
OrderDate = DateTime.Now;
OrderItems = new List<OrderItem>();
}
public void AddItem(OrderItem item)
{
OrderItems.Add(item);
}
public void PlaceOrder()
{
// Raise the OrderPlacedEvent when the order is placed
var orderPlacedEvent = new OrderPlacedEvent(OrderId, CustomerId, OrderDate);
_domainEvents.Add(orderPlacedEvent);
}
public void ClearDomainEvents()
{
_domainEvents.Clear();
}
}
```

The Order aggregate raises a Domain Event when an order is placed.

### Step 2: Define Domain Events

**Domain Events** are raised when something significant happens in the domain (e.g., an order is placed). These events can be handled by other parts of the system, such as inventory or notification services.

```csharp
public class OrderPlacedEvent
{
public Guid OrderId { get; }
public Guid CustomerId { get; }
public DateTime OrderDate { get; }
public OrderPlacedEvent(Guid orderId, Guid customerId, DateTime orderDate)
{
OrderId = orderId;
CustomerId = customerId;
OrderDate = orderDate;
}
}
```

### Step 3: Implement Command Handlers (Write Side of CQRS)

The **Command Handlers** handle commands (actions that modify the state of the system). For example, the command to place an order:

```csharp
public class PlaceOrderCommand
{
public Guid CustomerId { get; set; }
public List<OrderItem> Items { get; set; }
}
public class PlaceOrderCommandHandler
{
private readonly IOrderRepository _orderRepository;
private readonly DomainEventDispatcher _eventDispatcher;
public PlaceOrderCommandHandler(IOrderRepository orderRepository, DomainEventDispatcher eventDispatcher)
{
_orderRepository = orderRepository;
_eventDispatcher = eventDispatcher;
}
public void Handle(PlaceOrderCommand command)
{
// Create a new order
var order = new Order(command.CustomerId);
foreach (var item in command.Items)
{
order.AddItem(item);
}
// Place the order
order.PlaceOrder();
// Save the order to the repository
_orderRepository.Save(order);
// Dispatch domain events (like OrderPlacedEvent)
foreach (var domainEvent in order.DomainEvents)
{
_eventDispatcher.Dispatch(domainEvent);
}
// Clear domain events after dispatching
order.ClearDomainEvents();
}
}
```

The PlaceOrderCommandHandler is responsible for handling the PlaceOrderCommand, raising domain events, and dispatching them to the appropriate handlers.

### Step 4: Implement Event Handlers for Domain Events

**Domain Event Handlers** handle domain events raised by the domain. For example, when an OrderPlacedEvent is raised, we might handle it by updating the inventory and notifying the customer.

```csharp
public class InventoryUpdateHandler
{
public void Handle(OrderPlacedEvent domainEvent)
{
Console.WriteLine($"Updating inventory for Order ID: {domainEvent.OrderId}");
// Logic to update inventory based on the placed order
}
}
public class EmailNotificationHandler
{
public void Handle(OrderPlacedEvent domainEvent)
{
Console.WriteLine($"Sending confirmation email to Customer ID: {domainEvent.CustomerId}");
// Logic to send email notification
}
}
```

### Step 5: Implement the Query Side (Read Model) of CQRS

The **Query Side** of **CQRS** deals with retrieving data. It is optimized for reading data, and often has its own database that is separate from the write model.

```csharp
public class OrderQueryModel
{
public Guid OrderId { get; set; }
public Guid CustomerId { get; set; }
public DateTime OrderDate { get; set; }
public List<OrderItem> Items { get; set; }
}
public class OrderQueryHandler
{
private readonly IOrderQueryRepository _queryRepository;
public OrderQueryHandler(IOrderQueryRepository queryRepository)
{
_queryRepository = queryRepository;
}
public OrderQueryModel Handle(GetOrderByIdQuery query)
{
// Retrieve the read model for the order
return _queryRepository.GetById(query.OrderId);
}
}
public class GetOrderByIdQuery
{
public Guid OrderId { get; }
public GetOrderByIdQuery(Guid orderId)
{
OrderId = orderId;
}
}
```

The OrderQueryHandler retrieves data from the **read database** optimized for fast queries.

### Step 6: Dispatch Domain Events

To manage **domain event dispatching**, create a **Domain Event Dispatcher** that invokes the appropriate event handler for each domain event.

```csharp
public class DomainEventDispatcher
{
private readonly IEnumerable<object> _handlers;
public DomainEventDispatcher(IEnumerable<object> handlers)
{
_handlers = handlers;
}
public void Dispatch(object domainEvent)
{
foreach (var handler in _handlers)
{
var handlerType = handler.GetType();
var eventType = domainEvent.GetType();
var method = handlerType.GetMethod("Handle", new[] { eventType });
if (method != null)
{
method.Invoke(handler, new[] { domainEvent });
}
}
}
}
```

The dispatcher invokes the correct Handle method based on the type of domain event.

### Step 7: Wiring It All Up (Dependency Injection and Configuration)

You need to register the command handlers, event handlers, and the dispatcher in **Startup.cs** or through your dependency injection container.

```csharp
public void ConfigureServices(IServiceCollection services)
{
// Register the command handler
services.AddScoped<PlaceOrderCommandHandler>();
// Register the event handlers
services.AddScoped<InventoryUpdateHandler>();
services.AddScoped<EmailNotificationHandler>();
// Register the event dispatcher with the handlers
services.AddScoped<DomainEventDispatcher>(provider =>
{
var handlers = new List<object>
{
provider.GetService<InventoryUpdateHandler>(),
provider.GetService<EmailNotificationHandler>()
};
return new DomainEventDispatcher(handlers);
});
// Register the query handler
services.AddScoped<OrderQueryHandler>();
}
```

### Step 8: Flow of Execution

1.  A PlaceOrderCommand is sent to the **Command Handler** (PlaceOrderCommandHandler).

2.  The command handler creates an Order aggregate and raises an OrderPlacedEvent.

3.  The **Domain Event Dispatcher** dispatches the event to the registered event handlers:

    - InventoryUpdateHandler: Updates the inventory.

    - EmailNotificationHandler: Sends a confirmation email.

4.  The **Read Model** (using the OrderQueryHandler) is updated based on the event, and future queries are handled separately from the write model.

### Conclusion

By combining **DDD**, **CQRS**, and **Domain Events**:

- You decouple the **write** model from the **read** model.

- You keep the domain model clean by triggering **Domain Events** within aggregates.

- Event handlers manage side effects (like updating inventory or sending notifications), making the system more modular and easier to maintain.

- This architecture improves **scalability**, **performance**, and **separation of concerns** in your .NET Core application.

This approach works well for complex systems, especially when there are many interconnected components that can benefit from event-driven communication.

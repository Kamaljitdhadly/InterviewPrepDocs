# .NET Core JSON Web Token

JWT (JSON Web Token) is a compact, URL-safe means of representing claims to be transferred between two parties. JWTs are often used for authentication and authorization in web applications. They consist of three parts: the header, the payload, and the signature.

### 1. Header

The header typically consists of two parts:

- **alg**: The signing algorithm used to secure the token, such as HMAC SHA256 or RSA.

- **typ**: The type of token, which is usually set to "JWT".

#### Example Header

```csharp
{
"alg": "HS256",
```

"typ": "JWT"

```csharp
}
```

This header indicates that the token is a JWT and uses the HMAC SHA256 algorithm for signing.

### 2. Payload

The payload is where the claims are stored. Claims are statements about an entity (typically, the user) and additional data. There are three types of claims:

- **Registered claims**: Predefined claims that are not mandatory but recommended, such as iss (issuer), exp (expiration time), and sub (subject).

- **Public claims**: Claims defined by the JWT specification, but can be used and interpreted by any party.

- **Private claims**: Custom claims created to share information between parties that agree on using them.

#### Example Payload

```csharp
{
"sub": "1234567890",
"name": "John Doe",
"admin": true,
```

"iat": 1693872000

```csharp
}
```

In this example:

- sub: Subject (user ID) which is "1234567890".

- name: The user's name, "John Doe".

- admin: A custom claim indicating if the user is an admin, which is true.

- iat: Issued At, a timestamp that shows when the JWT was issued (1693872000).

### 3. Signature

The signature is used to verify that the token wasn’t altered. It’s created by taking the encoded header, the encoded payload, a secret key, and the algorithm specified in the header.

The signature is computed as follows:

HMACSHA256(

base64UrlEncode(header) + "." + base64UrlEncode(payload),

secret

)

If someone tries to tamper with the header or payload, the signature will no longer match, and the token will be considered invalid.

#### Example Signature

Suppose the secret key is "your-256-bit-secret". The signature might look something like this after encoding:

SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

### How JWTs Are Used

- **Authentication**: After a user logs in, a JWT is generated and sent to the client. The client then includes the JWT in the Authorization header of subsequent requests (Authorization: Bearer <token>).

- **Validation**: The server validates the JWT by verifying its signature and checking the claims (e.g., expiration time). If the JWT is valid, the server processes the request.

---------------------------------------------------------------------------------------------------------------------------------------------------

Within the payload, there are several standard claims that provide information about the token. The key claims include:

1.  **Issuer (iss)**: The entity that issued the JWT. This is usually the authentication server or the identity provider (IDP).

2.  **Audience (aud)**: The intended recipient of the token. This ensures that the token is only accepted by certain recipients.

3.  **Subject (sub)**: The principal or user the token is representing. This is usually the user who is authenticated and authorized.

### Example Scenario

Suppose you have a web application where users need to log in to access their dashboard. You use JWT for this purpose.

1.  **Issuer (iss)**:

    - The issuer is your authentication server, which might be https://auth.example.com. This tells whoever receives the JWT that it was generated and signed by auth.example.com.

2.  **Audience (aud)**:

    - The audience is your web application, which might be identified as https://app.example.com. This ensures that the token is only valid for requests made to your web application and not to other services.

3.  **Subject (sub)**:

    - The subject could be the user's unique identifier in your system, such as a user ID. For example, if the user John Doe has a user ID of 12345, the sub claim might be 12345. This indicates that the JWT is associated with John Doe.

### Example JWT Payload

Here’s what the payload of a JWT might look like with these claims:

```csharp
{
"iss": "https://auth.example.com",
"aud": "https://app.example.com",
"sub": "12345",
```

"exp": 1693958400, // Expiration time as Unix timestamp

"iat": 1693872000, // Issued at time as Unix timestamp

"role": "user"

```csharp
}
```

- iss: https://auth.example.com (The issuer of the token)

- aud: https://app.example.com (The audience for which the token is intended)

- sub: 12345 (The subject, typically the user ID)

- exp: The expiration time, ensuring the token is only valid for a certain period.

- iat: The time the token was issued, used to validate the token’s age.

- role: Custom claim that indicates the role of the user, such as user, admin, etc.

### How It's Used

- **Issuer Validation**: When your application receives a JWT, it checks the iss claim to ensure that the token was issued by a trusted entity (https://auth.example.com).

- **Audience Validation**: The application also checks the aud claim to ensure the token is intended for it (https://app.example.com).

- **Subject Validation**: The application uses the sub claim to identify the user making the request (12345), and might look up the user's details in a database.

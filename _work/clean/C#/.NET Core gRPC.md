# gRPC Concepts Explained with Examples

gRPC (gRPC Remote Procedure Calls) is a framework for building distributed applications and services. It allows clients and servers to communicate using a well-defined contract (Protocol Buffers) and uses HTTP/2 as its transport layer for efficient communication.

Here are the key concepts of gRPC along with examples:

### 1. Protocol Buffers (Protobuf)

Protobuf is an Interface Definition Language (IDL) used by gRPC to define the structure of messages and services. It’s a language-neutral, platform-neutral, and extensible mechanism for serializing structured data.

### Example of Protobuf (Message and Service Definitions)

syntax = "proto3";

option csharp_namespace = "GrpcService";

// Request message

```csharp
message HelloRequest {
  string name = 1;
}
// Response message
message HelloReply {
  string message = 1;
}
// gRPC service definition
service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply);
}
```

- **HelloRequest**: Defines the request with one field name.

- **HelloReply**: Defines the response with one field message.

- **Greeter**: A gRPC service with a method SayHello that takes a HelloRequest and returns a HelloReply.

When you compile this .proto file, gRPC will generate C# classes to use in your application.

### 2. Service Definition

In gRPC, you define a service in the .proto file, which consists of remote procedure calls (RPCs) that the server implements. The client can call these methods as if they are local.

### Example Service (gRPC Server-Side Implementation)

```csharp
public class GreeterService : Greeter.GreeterBase
{
  public override Task<HelloReply> SayHello(HelloRequest request, ServerCallContext context)
  {
    return Task.FromResult(new HelloReply
    {
      Message = $"Hello, {request.Name}"
    });
  }
}
```

- **SayHello Method**: Implements the RPC defined in the .proto file, which takes a HelloRequest and returns a HelloReply. In this example, it returns a greeting message based on the request.

### 3. gRPC Communication Types

gRPC supports four communication types (RPC types):

### A. Unary RPC (Request-Response)

The most basic form of gRPC communication where the client sends a single request and receives a single response from the server.

### Example

```csharp
service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply);
}
```

Client makes a single request and gets a single response:

```csharp
var reply = await client.SayHelloAsync(new HelloRequest { Name = "John" });
```

### B. Server Streaming RPC

The client sends a single request, but the server responds with a stream of responses. The client reads the stream until it’s done.

### Example

```csharp
service Greeter {
  rpc GetMessages (HelloRequest) returns (stream HelloReply);
}
```

Server streams multiple responses for a single request:

```csharp
public override async Task GetMessages(HelloRequest request, IServerStreamWriter<HelloReply> responseStream, ServerCallContext context)
{
  for (int i = 0; i < 5; i++)
  {
    await responseStream.WriteAsync(new HelloReply { Message = $"Message {i} for {request.Name}" });
    await Task.Delay(1000); // Simulate some processing time
  }
}
```

- The server sends five messages to the client.

### C. Client Streaming RPC

The client sends a stream of requests to the server. Once the client finishes sending the stream, the server processes it and sends back a single response.

### Example

```csharp
service Greeter {
  rpc UploadMessages (stream HelloRequest) returns (HelloReply);
}
```

Client streams multiple requests to the server:

```csharp
var call = client.UploadMessages();
foreach (var message in messages)
{
  await call.RequestStream.WriteAsync(new HelloRequest { Name = message });
}
await call.RequestStream.CompleteAsync();
var response = await call.ResponseAsync;
Console.WriteLine($"Response: {response.Message}");
```

- The client sends multiple HelloRequest messages, and the server responds once the stream is completed.

### D. Bidirectional Streaming RPC

Both the client and server send a stream of messages to each other. They operate independently, so the client and server can read and write messages in any order.

### Example

```csharp
service Greeter {
  rpc Chat (stream HelloRequest) returns (stream HelloReply);
}
```

Both the client and server stream messages to each other:

```csharp
public override async Task Chat(IAsyncStreamReader<HelloRequest> requestStream, IServerStreamWriter<HelloReply> responseStream, ServerCallContext context)
{
  while (await requestStream.MoveNext())
  {
    var request = requestStream.Current;
    await responseStream.WriteAsync(new HelloReply { Message = $"Hello, {request.Name}" });
  }
}
```

### 4. HTTP/2 Support

gRPC uses **HTTP/2** as its transport layer, which offers the following advantages:

- **Multiplexing**: Multiple requests and responses can be sent over a single connection.

- **Header Compression**: Reduces the size of metadata.

- **Server Push**: Server can push responses without explicit client requests.

To ensure your application runs over HTTP/2, make sure the server is configured properly. For example, in appsettings.json:

```csharp
    "EndpointDefaults": {
```

### 5. Performance and Scalability

gRPC is designed to be lightweight and efficient:

- **Binary Format (Protobuf)**: It uses Protocol Buffers, which are more compact and efficient than JSON.

- **Streaming**: Supports streaming, allowing continuous data flow between client and server.

- **Asynchronous Communication**: gRPC methods are asynchronous, allowing for high-concurrency.

### 6. Client Stub

When a .proto file is compiled, it generates client stubs (C# classes) that allow you to call gRPC services just like local methods.

### Example (gRPC Client)

### 7. Metadata and Interceptors

gRPC supports **metadata**, which is additional key-value pairs sent with requests or responses. Metadata is useful for authentication, tracing, and other cross-cutting concerns.

You can also use **interceptors** to implement common concerns like logging or authorization.

### Example of Sending Metadata (Client-Side)


### 1. Deadlines and Timeouts

gRPC allows clients to set **deadlines** (or timeouts) for RPC calls, which means the client can specify how long it is willing to wait for a response before giving up.

### Example (Setting Deadlines/Timeouts)

```csharp
var deadline = DateTime.UtcNow.AddSeconds(5);
var reply = await client.SayHelloAsync(new HelloRequest { Name = "John" }, deadline: deadline);
```

- **deadline**: This specifies the time the client is willing to wait for the server response (5 seconds in this case). If the server does not respond in time, an exception is thrown (RpcException).

### 2. Cancellation

Clients can cancel an in-progress gRPC call. This is useful when the client no longer needs the response or if the call is taking too long.

### Example (Cancelling RPC)

```csharp
var cts = new CancellationTokenSource();
var call = client.SayHelloAsync(new HelloRequest { Name = "John" }, cancellationToken: cts.Token);
// Cancel the call after 1 second
cts.CancelAfter(TimeSpan.FromSeconds(1));
try
{
  var reply = await call.ResponseAsync;
  Console.WriteLine($"Reply: {reply.Message}");
}
catch (RpcException ex) when (ex.StatusCode == StatusCode.Cancelled)
{
  Console.WriteLine("Call was cancelled.");
}
```

- **CancellationToken**: Allows you to cancel the request from the client side if it's taking too long or the user interrupts the process.

### 3. Load Balancing

In a microservices or distributed system, it’s common to distribute gRPC calls across multiple servers for scaling. gRPC supports load balancing in several ways:

### A. Client-Side Load Balancing

gRPC clients can load balance requests across multiple server endpoints.

To enable client-side load balancing, you must use **multiple backends** with DNS-based load balancing.

### Example (Client-Side Load Balancing)

```csharp
var channel = GrpcChannel.ForAddress("dns:///my-backend-service", new GrpcChannelOptions
{
  Credentials = ChannelCredentials.Insecure
});
```

In this case, my-backend-service is a DNS entry that resolves to multiple IP addresses, distributing the load across available instances.

### 4. gRPC Reflection

gRPC **reflection** allows clients to dynamically discover service definitions without needing the .proto file. This is particularly useful for tools like grpcurl and client-side introspection.

To enable reflection, you need to add the Grpc.AspNetCore.Server.Reflection package to your server and configure it in Startup.cs.

### Example (Enabling Reflection)

1.  Install the NuGet package:

```csharp
dotnet add package Grpc.AspNetCore.Server.Reflection
```

2.  Configure in Startup.cs:

```csharp
public void ConfigureServices(IServiceCollection services)
{
  services.AddGrpc();
  services.AddGrpcReflection();
}
public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
{
  app.UseRouting();
  app.UseEndpoints(endpoints =>
  {
    endpoints.MapGrpcService<GreeterService>();
    // Enable reflection in development mode
    if (env.IsDevelopment())
    {
      endpoints.MapGrpcReflectionService();
    }
  });
}
```

Reflection is useful for debugging and testing tools to dynamically interact with your gRPC services.

### 5. gRPC-Web

By default, gRPC runs over HTTP/2, which is not fully supported by web browsers. **gRPC-Web** is an extension that allows gRPC to work with browsers by providing a bridge between HTTP/2 and HTTP/1.1.

This enables browser-based front-end clients to consume gRPC services via JavaScript.

### Steps to Enable gRPC-Web

1.  Install the **gRPC-Web** NuGet package:

```csharp
dotnet add package Grpc.AspNetCore.Web
```

2.  Enable gRPC-Web in Startup.cs:

```csharp
public void ConfigureServices(IServiceCollection services)
{
  services.AddGrpc();
}
public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
{
  app.UseRouting();
  app.UseGrpcWeb(); // Enable gRPC-Web support
  app.UseEndpoints(endpoints =>
  {
    endpoints.MapGrpcService<GreeterService>()
    .EnableGrpcWeb(); // Enable gRPC-Web for specific services
  });
}
```

3.  From the client side, you can use the [<u>gRPC-Web client library</u>](https://github.com/grpc/grpc-web) to interact with the service using JavaScript.

### 7. Interceptors

**Interceptors** allow you to add cross-cutting logic (like logging, monitoring, or authorization) to your gRPC calls.

Interceptors intercept incoming or outgoing calls and let you add custom behavior.

### Example (Logging Interceptor)

```csharp
public class LoggingInterceptor : Interceptor
{
  public override async Task<TResponse> UnaryServerHandler<TRequest, TResponse>(
  TRequest request,
  ServerCallContext context,
  UnaryServerMethod<TRequest, TResponse> continuation)
  {
    Console.WriteLine("Starting call...");
    var response = await continuation(request, context);
    Console.WriteLine("Call finished.");
    return response;
  }
}
```

You can register the interceptor in Startup.cs:

```csharp
services.AddGrpc(options =>
{
  options.Interceptors.Add<LoggingInterceptor>();
});
```

Interceptors are extremely powerful for handling authentication, validation, logging, metrics collection, and more.

### 8. Compression

gRPC allows you to **compress** messages to optimize network bandwidth, particularly useful for large payloads.

You can configure compression by specifying it in the call:

### Server-Side Compression

```csharp
var reply = new HelloReply { Message = "Hello" };
context.WriteOptions = new WriteOptions(WriteFlags.UseCompression);
await responseStream.WriteAsync(reply);
```

### Client-Side Compression

```csharp
var callOptions = new CallOptions()
.WithWriteOptions(new WriteOptions(WriteFlags.UseCompression));
var reply = await client.SayHelloAsync(new HelloRequest { Name = "John" }, callOptions);
```

This helps to reduce the payload size, especially in scenarios where bandwidth is limited.

### 9. Error Handling with Status Codes

gRPC uses **status codes** to handle errors gracefully. Each RpcException comes with a status code indicating the type of error (similar to HTTP status codes).

Common status codes:

- StatusCode.OK: Successful call.

- StatusCode.InvalidArgument: The client provided an invalid argument.

- StatusCode.NotFound: A requested entity (e.g., a resource) was not found.

- StatusCode.Internal: Internal server error.

- StatusCode.Unavailable: The service is currently unavailable.

### Example (Returning Error from Server)

```csharp
public override Task<HelloReply> SayHello(HelloRequest request, ServerCallContext context)
{
  if (string.IsNullOrWhiteSpace(request.Name))
  {
    throw new RpcException(new Status(StatusCode.InvalidArgument, "Name cannot be empty"));
  }
  return Task.FromResult(new HelloReply
  {
    Message = $"Hello, {request.Name}"
  });
}
```

Handling errors this way ensures the client gets meaningful feedback on what went wrong.

### 2. **Bi-Directional Streaming with Custom Control Logic**

gRPC supports **bi-directional streaming**, allowing both the client and server to send and receive messages independently. Here’s an advanced use case where the client streams data, and the server processes it in batches.

#### Example: Bi-Directional Streaming with Flow Control

```csharp
public class StreamService : StreamService.StreamServiceBase
{
  public override async Task BidirectionalStreaming(IAsyncStreamReader<DataRequest> requestStream, IServerStreamWriter<DataResponse> responseStream, ServerCallContext context)
  {
    var batch = new List<string>();
    await foreach (var request in requestStream.ReadAllAsync())
    {
      batch.Add(request.Data);
      if (batch.Count >= 5) // Process in batches of 5
      {
        // Process the batch (e.g., save to a database)
        await ProcessBatch(batch);
        // Send acknowledgment back to the client
        await responseStream.WriteAsync(new DataResponse { Status = "Batch processed" });
        batch.Clear();
      }
    }
    // Final batch processing if any items remain
    if (batch.Count > 0)
    {
      await ProcessBatch(batch);
      await responseStream.WriteAsync(new DataResponse { Status = "Final batch processed" });
    }
  }
  private Task ProcessBatch(List<string> batch)
  {
    Console.WriteLine($"Processing batch of size {batch.Count}");
    return Task.CompletedTask;
  }
}
```

Here, the server waits until it receives a batch of 5 items from the client before processing and acknowledging back. This kind of logic is useful for efficiently handling large data streams in chunks, ensuring the client doesn’t overload the server with requests.

On the client side:

```csharp
using var call = client.BidirectionalStreaming();
for (int i = 0; i < 12; i++)
{
  await call.RequestStream.WriteAsync(new DataRequest { Data = $"Message {i + 1}" });
}
// Signal the end of the data stream
await call.RequestStream.CompleteAsync();
// Read responses from the server
await foreach (var response in call.ResponseStream.ReadAllAsync())
{
  Console.WriteLine(response.Status);
}
```

This client sends 12 messages in total, and the server processes them in batches of 5. The last 2 remaining messages will be processed when the stream is completed.

### 3. **Interceptors for Request Logging and Custom Error Handling**

**Interceptors** allow you to add custom behavior to gRPC requests, such as logging, authentication, or modifying request/response payloads.

#### Example: Logging and Error Handling Interceptor

```csharp
public class LoggingInterceptor : Interceptor
{
  private readonly ILogger<LoggingInterceptor> _logger;
  public LoggingInterceptor(ILogger<LoggingInterceptor> logger)
  {
    _logger = logger;
  }
  public override async Task<TResponse> UnaryServerHandler<TRequest, TResponse>(
  TRequest request,
  ServerCallContext context,
  UnaryServerMethod<TRequest, TResponse> continuation)
  {
    _logger.LogInformation($"Starting call. Method: {context.Method}, Request: {request}");
    try
    {
      var response = await continuation(request, context);
      _logger.LogInformation($"Completed call. Response: {response}");
      return response;
    }
    catch (RpcException ex)
    {
      _logger.LogError($"Error during call. Status: {ex.Status}, Message: {ex.Message}");
      throw;
    }
  }
}
```

You register this interceptor in the Startup.cs:

```csharp
services.AddGrpc(options =>
{
  options.Interceptors.Add<LoggingInterceptor>();
});
```

This interceptor logs incoming gRPC requests and responses, as well as handles errors. You can extend it to handle retries, add metadata, or perform authentication checks.

### 4. **Deadlines with Retry Logic**

In gRPC, **deadlines** are used to specify the maximum time a client is willing to wait for an RPC call. Combined with retries, you can build robust systems where the client retries a failed call within a deadline.

#### Example: Implementing Deadlines and Retries

```csharp
var deadline = DateTime.UtcNow.AddSeconds(5);
var callOptions = new CallOptions()
.WithDeadline(deadline)
.WithRetryPolicy(new RetryPolicyConfig
{
  MaxAttempts = 3,
  InitialBackoff = TimeSpan.FromMilliseconds(100),
  MaxBackoff = TimeSpan.FromMilliseconds(500),
  BackoffMultiplier = 1.5,
  RetryableStatusCodes = { StatusCode.Unavailable, StatusCode.DeadlineExceeded }
});
var response = await client.SayHelloAsync(new HelloRequest { Name = "Bob" }, callOptions);
```

In this example:

- The client sets a **deadline** of 5 seconds for the request.

- The client retries the call up to 3 times if it encounters transient failures (e.g., Unavailable or DeadlineExceeded).

Retries can improve the robustness of your system, especially in microservices environments where network failures are common.

### 5. **gRPC Security with TLS and JWT Authentication**

Securing gRPC services involves using **TLS** for encryption and **JWT** tokens for authentication. This ensures data confidentiality and integrity as well as proper client authorization.

#### Example: Enabling TLS and JWT Authentication

##### Step 1: Server-Side TLS Configuration

```csharp
var server = new Server
{
  Services = { Greeter.BindService(new GreeterService()) },
  Ports = { new ServerPort("localhost", 50051, new SslServerCredentials(new List<KeyCertificatePair>
  {
    new KeyCertificatePair(
    File.ReadAllText("server.crt"),
    File.ReadAllText("server.key"))
  })) }
};
server.Start();
```

In this example, the server is configured with **TLS** using server.crt and server.key.

##### Step 2: Client-Side TLS Configuration

```csharp
var channel = new Channel("localhost:50051", new SslCredentials(File.ReadAllText("ca.crt")));
var client = new Greeter.GreeterClient(channel);
```

Here, the client establishes a secure connection to the server by using the **CA certificate** (ca.crt).

##### Step 3: Sending JWT Token with Requests

On top of TLS, we can add **JWT-based authentication**. The client attaches a token in the metadata:

```csharp
var headers = new Metadata
{
  { "Authorization", $"Bearer {jwtToken}" }
};
var reply = await client.SayHelloAsync(new HelloRequest { Name = "Alice" }, headers);
```

On the server side, you can validate the JWT token using middleware like ASP.NET Core’s **Authorization Middleware** to ensure the token is valid before processing the request.

# .NET Core Web Sockets

## Questions Covered

1. What is WebSocket and how does it work?
2. How does WebSocket messaging work in a chat application?
3. How do you maintain WebSocket connections?
4. How do group messages work?

## What is WebSocket and how does it work?

**WebSocket** enables **full-duplex** communication over a single long-lived connection between client (browser/app) and server. Unlike HTTP's request-response model, both sides send data simultaneously — ideal for real-time apps (chat, live feeds, gaming).

## How does WebSocket messaging work in a chat application?

**Connection establishment:** on login, client opens a WebSocket to the server; connection stays open while online.

**User A → User B direct message:**

1. **Send** — User A transmits over the open WebSocket.
2. **Process** — server checks if User B is online with an active connection.
3. **Deliver:**
   - **Online** — forward immediately via User B's WebSocket.
   - **Offline** — store in DB (e.g., MongoDB); optionally trigger push notification.
4. **Acknowledge** — server confirms delivery (or queued storage) to User A.

## How do you maintain WebSocket connections?

**Tracking connections** — associate each WebSocket with a user session. Store in fast in-memory store (e.g., **Redis**):

- **User ID** — identify the user
- **Connection ID** — unique per connection
- **Session metadata** — device ID, timestamp, etc.

**Multiple devices** — one user may have several connections (phone, tablet). Store as a list/set of connection IDs per user ID.

**Disconnections** — remove connection data when user goes offline or connection closes; optionally notify client and clean session data.

## How do group messages work?

**Sending a group message:**

1. User A sends message + group ID to server.
2. Server fetches group members; checks who is online.
3. **Deliver** — forward to online members via their WebSockets; store for offline members.
4. **Notify** — push notifications for offline members.

**Message storage** — persist with group ID, sender ID, content, timestamp (NoSQL document with message list per group).

**Delivery receipts** — track per-member received/read status (message ID, recipient ID, delivery/read flags); update as members receive and read.

**Fan-out strategies:**

| Strategy | Behavior | Trade-off |
|----------|----------|-----------|
| **Fan-out on Write** | Send to all online immediately; store for offline | Near-instant delivery; more immediate processing |
| **Fan-out on Read** | Store message; deliver when member comes online or requests history | Lower immediate load; slight delay for some users |

**Summary:**

- WebSocket = real-time full-duplex messaging
- Redis (or similar) tracks connections for routing
- Direct messages: deliver live or queue + push notify
- Group messages: fan-out to members with online/offline handling and read receipts

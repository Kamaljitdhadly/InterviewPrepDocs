## What are the three parts of a JWT and how do they work?

A **JWT (JSON Web Token)** is a compact, URL-safe way to transfer claims between parties — commonly used for authentication and authorization. Three parts: **header**, **payload**, **signature** (joined by `.`).

### Header

Signing algorithm and token type:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- `alg` — signing algorithm (HMAC SHA256, RSA, etc.)
- `typ` — always `"JWT"`

### Payload

Contains **claims** — statements about an entity (usually the user):

- **Registered** — `iss`, `exp`, `sub` (recommended standard claims)
- **Public** — defined by JWT spec, usable by any party
- **Private** — custom claims agreed between parties

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "iat": 1693872000
}
```

- `sub` — subject (user ID)
- `name` — custom claim
- `admin` — custom boolean claim
- `iat` — issued-at timestamp

### Signature

Verifies the token wasn't tampered with:

```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```

Tampering with header/payload invalidates the signature.

**Example signature:** `SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

### Full JWT

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTY5Mzg3MjAwMH0
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

| Part | Encoded | Decoded |
|------|---------|---------|
| Header | `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9` | `{"alg":"HS256","typ":"JWT"}` |
| Payload | `eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTY5Mzg3MjAwMH0` | `{"sub":"1234567890","name":"John Doe","admin":true,"iat":1693872000}` |
| Signature | `SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c` | — |

**Usage:**

- **Authentication** — after login, server issues JWT; client sends `Authorization: Bearer <token>` on subsequent requests
- **Validation** — server verifies signature and claims (e.g., `exp`); processes request if valid

## What are iss, aud, and sub claims and how are they validated?

Key standard claims in the payload:

| Claim | Meaning |
|-------|---------|
| **iss** (issuer) | Entity that issued the JWT (auth server / IDP) |
| **aud** (audience) | Intended recipient — token accepted only by this app/service |
| **sub** (subject) | Principal the token represents (usually user ID) |

**Example scenario** — user logs in to access a dashboard:

- `iss`: `https://auth.example.com` — token signed by auth server
- `aud`: `https://app.example.com` — token valid only for this app
- `sub`: `12345` — user ID (e.g., John Doe)

```json
{
  "iss": "https://auth.example.com",
  "aud": "https://app.example.com",
  "sub": "12345",
  "exp": 1693958400,
  "iat": 1693872000,
  "role": "user"
}
```

- `exp` — expiration (Unix timestamp)
- `iat` — issued-at time
- `role` — custom claim

**Validation on receipt:**

- **iss** — ensure token came from trusted issuer (`https://auth.example.com`)
- **aud** — ensure token is intended for this application
- **sub** — identify the user (`12345`); look up details in database if needed

## What are the OAuth 2.0 roles and how does the Authorization Code Flow work (Angular + .NET + Google)?

OAuth 2.0 is an authorization framework where a **client** obtains limited access to a **resource server** on behalf of a **resource owner**, mediated by an **authorization server**. The **Authorization Code Grant** is the most secure flow for web apps with a back-end — the client secret never reaches the browser.

**Roles in this example:**

| Role | Example |
|------|---------|
| Client | Angular (`app.bluestone.com`) + .NET Core (`api.bluestone.com`) |
| Resource owner | User |
| Authorization server | Google (`identity.google.com`) |
| Resource server | Google APIs (`api.google.com`) |

**Authorization Code Flow (8 steps):**

1. **User initiates login** — Angular redirects to Google:

```http
GET https://accounts.google.com/o/oauth2/auth?
  response_type=code&
  client_id=YOUR_GOOGLE_CLIENT_ID&
  redirect_uri=https://app.bluestone.com/callback&
  scope=email profile&
  state=xyz123
```

- `response_type=code` — request authorization code
- `client_id` — app ID from Google
- `redirect_uri` — callback URL after auth
- `scope` — requested permissions
- `state` — CSRF protection

2. **User authenticates** — Google redirects back:

```http
https://app.bluestone.com/callback?code=AUTH_CODE&state=xyz123
```

3. **Angular sends code to .NET backend:**

```typescript
this.http.post('https://api.bluestone.com/token', {
  code: 'AUTH_CODE',
  redirect_uri: 'https://app.bluestone.com/callback',
  client_id: 'YOUR_GOOGLE_CLIENT_ID',
  client_secret: 'YOUR_GOOGLE_CLIENT_SECRET'
}).subscribe((response: any) => {
  const accessToken = response.access_token;
});
```

4. **.NET exchanges code with Google:**

```http
POST https://oauth2.googleapis.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=AUTH_CODE&
redirect_uri=https://app.bluestone.com/callback&
client_id=YOUR_GOOGLE_CLIENT_ID&
client_secret=YOUR_GOOGLE_CLIENT_SECRET
```

5. **Google returns tokens:**

```json
{
  "access_token": "ACCESS_TOKEN",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "REFRESH_TOKEN",
  "scope": "email profile"
}
```

6. **.NET forwards token to Angular:**

```json
{ "access_token": "ACCESS_TOKEN" }
```

7. **Angular calls Google API:**

```typescript
this.http.get('https://www.googleapis.com/oauth2/v2/userinfo', {
  headers: { Authorization: 'Bearer ACCESS_TOKEN' }
}).subscribe(userInfo => console.log(userInfo));
```

8. **Google validates token and returns data:**

```json
{
  "id": "123456789",
  "email": "user@example.com",
  "name": "John Doe",
  "picture": "https://example.com/photo.jpg"
}
```

## What is the Implicit Grant Flow and when is it used?

Used by **SPAs** that cannot securely store a client secret. The key difference from Authorization Code: the access token is returned **directly** in the redirect URI fragment — no intermediate code exchange on a back-end. The access token is returned **directly in the redirect URI fragment** — no authorization-code exchange.

**Workflow:**

1. Client redirects to authorization server:

```http
GET https://authserver.com/authorize?
  response_type=token&
  client_id=your-client-id&
  redirect_uri=https://app.bluestone.com/callback&
  scope=openid profile email&
  state=xyz123
```

2. User authenticates and grants consent.

3. Server redirects with token in URL **fragment**:

```http
https://app.bluestone.com/callback#access_token=abcd1234&token_type=Bearer&expires_in=3600&state=xyz123
```

4. Client extracts token from fragment; stores in memory/local storage.

5. Client uses token in API requests:

```http
GET https://api.bluestone.com/userinfo
Authorization: Bearer abcd1234
```

6. Token expires → user must re-authenticate (no refresh token).

**Key points:**

- Faster but less secure — access token exposed in URL fragment (not sent to server in HTTP request, but vulnerable in local storage or to malicious JS)
- Client cannot store a refresh token; access tokens must be short-lived
- Commonly used in Angular/React SPAs running entirely in the browser
- **PKCE + Authorization Code** is the modern replacement; implicit grant is being phased out

## What is Authorization Code Grant with PKCE?

Secure variant of Authorization Code Grant for **public clients** (SPAs, mobile) that cannot store secrets. **PKCE (Proof Key for Code Exchange)** ensures an intercepted authorization code can only be redeemed by the client that requested it. A **code verifier** proves only the requesting client can exchange the authorization code.

**Workflow:**

1. Client generates **code verifier** (random string) and **code challenge** (Base64 URL-encoded SHA-256 hash), then redirects:

```http
GET https://authserver.com/authorize?
  response_type=code&
  client_id=your-client-id&
  redirect_uri=https://app.bluestone.com/callback&
  scope=openid profile email&
  state=xyz123&
  code_challenge=JdRnHfK6Xm...&
  code_challenge_method=S256
```

2. User authenticates and authorizes.

3. Server redirects with code:

```http
https://app.bluestone.com/callback?code=abcd1234&state=xyz123
```

4. Client exchanges code + **code verifier**:

```http
POST https://authserver.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
client_id=your-client-id&
code=abcd1234&
redirect_uri=https://app.bluestone.com/callback&
code_verifier=xyz987K4dhgjjs...
```

5. Server validates challenge against verifier hash; issues tokens:

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "xyz0987",
  "scope": "openid profile email"
}
```

6. Client uses access token:

```http
GET https://api.bluestone.com/userinfo
Authorization: Bearer eyJhbGciOiJIUzI1...
```

**Code verifier/challenge example:**

- Verifier: `xyz987K4dhgjjsBdLfsflkdoeP...`
- Challenge: `JdRnHfK6Xm...` (Base64 URL-encoded SHA-256 of verifier)

**Benefits:** prevents code interception; no client secret needed; replaces implicit grant for SPAs.

## What is the Client Credentials Grant?

**Machine-to-machine** flow — no user interaction. Client authenticates with `client_id` + `client_secret` to get an access token.

**Use cases:** server-to-server API calls, background jobs, microservices.

1. **Request token:**

```http
POST https://authserver.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&
client_id=your-client-id&
client_secret=your-client-secret&
scope=api.read
```

2. **Token response:**

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "api.read"
}
```

3. **Access protected resource:**

```http
GET https://api.bluestone.com/resource
Authorization: Bearer eyJhbGciOiJIUzI1...
```

4. **API response:**

```json
{ "data": "Protected resource data" }
```

**Example scenario:** a .NET microservice calls an external API — it uses Client Credentials to obtain a token from IdentityServer/Azure AD, then calls the external API with that token.

**Security:** store `client_secret` securely (env vars/vault); limit scope (least privilege); use short-lived tokens.

## What is the Resource Owner Password Credentials (ROPC) Grant?

Client collects **username + password** and sends them directly to the authorization server. **Deprecated for public clients** — exposes user credentials to the application.

**Use case:** trusted first-party/legacy apps only.

1. Client collects credentials securely (HTTPS).

2. **Token request:**

```http
POST https://authserver.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=password&
client_id=your-client-id&
client_secret=your-client-secret&
username=user@example.com&
password=userpassword&
scope=api.read
```

3. **Token response:**

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "api.read"
}
```

4. **API request:**

```http
GET https://api.bluestone.com/userinfo
Authorization: Bearer eyJhbGciOiJIUzI1...
```

5. **API response:**

```json
{ "data": "User information data" }
```

**Example scenario:** a legacy desktop app authenticates users internally and passes credentials to the authorization server to get an access token for an external API.

**Security:** credentials exposed to client; HTTPS required; often no refresh token; not suitable for SPAs or public clients; prefer **Authorization Code + PKCE** for modern apps.

## What is the Refresh Token Grant?

Extends sessions without re-authentication. Client exchanges a **long-lived refresh token** for a new access token when the current one expires.

1. **Initial response** (from Authorization Code or similar):

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "ABCD1234REFRESH",
  "scope": "api.read"
}
```

2. **Refresh request** (after access token expires):

```http
POST https://authserver.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&
refresh_token=ABCD1234REFRESH&
client_id=your-client-id&
client_secret=your-client-secret
```

3. **New token response:**

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "NEWREFRESH1234",
  "scope": "api.read"
}
```

4. **Use new access token:**

```http
GET https://api.bluestone.com/resource
Authorization: Bearer eyJhbGciOiJIUzI1...
```

**Use cases:** keep users logged in without re-sign-in; reduce login frequency in mobile/desktop apps.

**Security:** store refresh tokens securely (encrypted DB, secure mobile storage); avoid exposing in public SPAs; limit refresh token scope; use **refresh token rotation** (new refresh token per exchange, old one invalidated).

## What is the Device Code Grant?

For **input-limited devices** (smart TVs, IoT, consoles). User authenticates on a secondary device (phone/PC).

1. **Device requests codes:**

```http
POST https://authserver.com/device_authorization
Content-Type: application/x-www-form-urlencoded

client_id=your-client-id&scope=openid profile email
```

```json
{
  "device_code": "GmRgDoLi2pqJwgzsl3NNpQnzgY4pRRvV",
  "user_code": "123456",
  "verification_uri": "https://authserver.com/device",
  "expires_in": 900,
  "interval": 5
}
```

2. Device displays: *"Go to https://authserver.com/device and enter code: 123456"*

3. User enters code on secondary device and logs in.

4. **Device polls:**

```http
POST https://authserver.com/token
Content-Type: application/x-www-form-urlencoded

client_id=your-client-id&
device_code=GmRgDoLi2pqJwgzsl3NNpQnzgY4pRRvV&
grant_type=urn:ietf:params:oauth:grant-type:device_code
```

**Poll responses:**

```json
{ "error": "authorization_pending" }
```

```json
{ "error": "slow_down" }
```

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "2YotnFZFEjr1zCsicMWpAA"
}
```

5. **Access API:**

```http
GET https://api.bluestone.com/resource
Authorization: Bearer eyJhbGciOiJIUzI1...
```

**Example (smart TV):** streaming app shows *"Go to authserver.com/device, enter ABC123"* → user logs in on phone → TV polls until it receives the access token and starts streaming.

**Security:** respect poll `interval`; handle `authorization_pending` and `slow_down` gracefully; codes expire in ~5–15 min; store tokens securely.

## What is the Hybrid Grant (OIDC)?

Combines **Authorization Code** (security) and **Implicit** (immediate token) flows. Used with **OpenID Connect** — front-end gets ID/access token immediately; back-end exchanges code for refresh token.

**Workflow:**

1. **Authorization request:**

```http
GET https://authserver.com/authorize?
  client_id=your-client-id&
  response_type=code id_token&
  redirect_uri=https://app.bluestone.com/callback&
  scope=openid profile email&
  state=xyzABC123&
  nonce=random-nonce
```

- `code id_token` — authorization code + ID token
- `code token` — authorization code + access token

2. **Redirect with code + token(s):**

```http
https://app.bluestone.com/callback?code=SplxlOBeZQQYbYS6WxSbIA&id_token=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...&state=xyzABC123
```

3. Front-end decodes ID token for user info; may use access token immediately.

4. **Back-end exchanges code:**

```http
POST https://authserver.com/token
Content-Type: application/x-www-form-urlencoded

client_id=your-client-id&
client_secret=your-client-secret&
grant_type=authorization_code&
code=SplxlOBeZQQYbYS6WxSbIA&
redirect_uri=https://app.bluestone.com/callback
```

5. **Back-end receives:**

```json
{
  "access_token": "eyJhbGciOiJIUzI1...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "2YotnFZFEjr1zCsicMWpAA"
}
```

6. Front-end may also call API directly:

```http
GET https://api.bluestone.com/resource
Authorization: Bearer eyJhbGciOiJIUzI1...
```

**Key characteristics:**

- ID token or access token can be sent directly to the client in the authorization response
- Authorization code is exchanged on the back-end for refresh token and additional tokens
- Sensitive tokens (refresh token) never reach the front-end

**Advantages:** immediate front-end access; refresh token stays on back-end only; combines Authorization Code security with Implicit immediacy.

```
Client (Browser)          Back-End API
     | 1. Auth Request          |
     |------------------------->|
     | 2. Code + ID/Access Token|
     |<-------------------------|
     | 3. Send Auth Code        |
     |------------------------->|
     |     4. Exchange Code     |
     |     (Access + Refresh)   |
```

## How does the authorization server determine whether to return an ID token or access token?

Determined by **scopes** and **response_type** in the authorization request.

**Scopes:**

- `openid` — OIDC; request **ID token** for authentication
- `profile`, `email` — additional claims in ID token
- `api.read`, `user.read` — OAuth scopes; request **access token** for APIs

**Response types:**

| response_type | Result |
|---------------|--------|
| `code` | Authorization code → exchanged for tokens |
| `token` | Access token directly (deprecated implicit) |
| `id_token` | ID token only (deprecated implicit OIDC) |
| `code id_token` | Hybrid — code + ID token |

**Example request:**

```http
GET /authorize?
  response_type=code&
  client_id=client123&
  redirect_uri=https://clientapp.com/callback&
  scope=openid profile api.read&
  state=xyz123
```

**Token exchange response:**

```json
{
  "id_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "access_token": "SlAV32hkKG...",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

**Scenarios:**

| Scope | Response Type | Tokens returned |
|-------|---------------|-----------------|
| `openid profile api.read` | `code` | ID token + access token |
| `api.read` | `code` | Access token only |
| `openid` | `id_token` | ID token only |

## Does AddJwtBearer validate JWT signatures when using Google as authority?

**Yes** — signature validation is automatic when `Authority` is set. The middleware fetches OIDC metadata from `https://accounts.google.com/.well-known/openid-configuration`, retrieves JWKS from `https://www.googleapis.com/oauth2/v3/certs`, and validates the signature against Google's public keys.

```csharp
public void ConfigureServices(IServiceCollection services)
{
    services.AddAuthentication(options =>
    {
        options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
        options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
    })
    .AddJwtBearer(options =>
    {
        options.Authority = "https://accounts.google.com";
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = "https://accounts.google.com",
            ValidateAudience = true,
            ValidAudience = "YOUR_GOOGLE_CLIENT_ID",
            ValidateLifetime = true,
        };
    });
    services.AddAuthorization();
    services.AddControllers();
}

public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
{
    app.UseRouting();
    app.UseAuthentication();
    app.UseAuthorization();
    app.UseEndpoints(endpoints => endpoints.MapControllers());
}
```

**Validated automatically:** issuer, audience, lifetime, and **signature** (via JWKS). No explicit signature config needed in `TokenValidationParameters`.

## How do you configure JWT Bearer authentication for IdentityServer4?

Same pattern as Google — point `Authority` to your IdentityServer; middleware discovers signing keys via OIDC metadata.

```csharp
services.AddAuthentication(options =>
{
    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
})
.AddJwtBearer(options =>
{
    options.Authority = "https://identity.bluestone.com";
    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidateIssuer = true,
        ValidIssuer = "https://identity.bluestone.com",
        ValidateAudience = true,
        ValidAudience = "bluestone.api",
        ValidateLifetime = true,
        ClockSkew = TimeSpan.Zero
    };
    options.Events = new JwtBearerEvents
    {
        OnAuthenticationFailed = context =>
        {
            Console.WriteLine("Token validation failed: " + context.Exception.Message);
            return Task.CompletedTask;
        },
        OnTokenValidated = context => Task.CompletedTask
    };
});
```

**Key points:**

- **Authority** → fetches `/.well-known/openid-configuration` and `jwks_uri` for public signing keys
- **ValidAudience** must match the `aud` claim (e.g., `bluestone.api`)
- Signature validation uses JWKS automatically

## What is the difference between AuthenticateScheme and ChallengeScheme?

| Scheme | Purpose |
|--------|---------|
| **AuthenticateScheme** | How to **verify** credentials on each request (read JWT from `Authorization` header, validate cookie, etc.) |
| **ChallengeScheme** | How to **prompt** authentication when missing/invalid (401 Unauthorized for JWT, redirect to login for cookies) |

```csharp
options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
// JWT Bearer used to authenticate incoming requests

options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
// JWT Bearer returns 401 when auth fails or is absent
```

**Authenticate** = validate existing credentials. **Challenge** = respond when auth is required but not provided.

## What is Memcache and how does it work?

**Memcache** is an in-memory key-value store that caches data to reduce database load and speed responses. Ideal when reads dominate writes and recomputation is expensive.

**How it works:**

1. **Storage** — key-value pairs in memory (strings, objects, query results).
2. **Retrieval** — check cache first; on **cache hit** return immediately; on **cache miss** fetch from DB/compute, then store for future requests.
3. **Expiration** — TTL prevents stale data indefinitely.

**Without Memcache:** every request hits the database.

**With Memcache:** first request may miss (DB query + cache store); subsequent requests hit cache.

```csharp
var productList = memcache.Get("productList");
if (productList == null)
{
    productList = database.Query("SELECT * FROM Products");
    memcache.Set("productList", productList, TimeSpan.FromMinutes(10));
}
return productList;
```

**Benefits:** faster retrieval, reduced DB load, better scalability, lower DB scaling costs.

**Limitations:** volatile (lost on restart); cache invalidation can be hard in dynamic apps.

## What are cache read policies?

### Cache Aside (Lazy Loading)

Application checks cache before DB. On miss, loads from DB and caches.

**When:** read-heavy, infrequently changing data.

```csharp
var product = cache.Get("product_123");
if (product == null)
{
    product = database.Query("SELECT * FROM Products WHERE id = 123");
    cache.Set("product_123", product, TimeSpan.FromMinutes(10));
}
return product;
```

- **Pros:** memory-efficient — only requested data cached.
- **Cons:** first-request latency on misses.

### Read-Through Cache

Cache itself loads from DB on miss, stores, and returns — centralizes caching logic.

```csharp
var product = cache.GetOrLoad("product_123", () =>
{
    return database.Query("SELECT * FROM Products WHERE id = 123");
}, TimeSpan.FromMinutes(10));
return product;
```

- **Pros:** simpler application code.
- **Cons:** cache can become a bottleneck if not tuned.

## What are cache write policies?

### Write-Through

Write to cache and DB simultaneously — always in sync.

```csharp
void UpdateProduct(Product product)
{
    database.Update(product);
    cache.Set("product_" + product.Id, product, TimeSpan.FromMinutes(10));
}
```

- **Pros:** strong consistency.
- **Cons:** higher write latency (two writes per update).

### Write-Behind (Write-Back)

Write to cache first; async write to DB later.

```csharp
void UpdateProduct(Product product)
{
    cache.Set("product_" + product.Id, product, TimeSpan.FromMinutes(10));
    Task.Run(() => database.Update(product));
}
```

- **Pros:** faster writes.
- **Cons:** risk of data loss if cache fails before DB persist.

### Write-Around

Write directly to DB; cache updated only on next read (cache-aside on read).

```csharp
void UpdateProduct(Product product)
{
    database.Update(product);
    cache.Remove("product_" + product.Id);
}
```

- **Pros:** fewer cache writes in write-heavy scenarios.
- **Cons:** more cache misses after writes.

| Policy | Read | Write |
|--------|------|-------|
| **Cache Aside** | App handles misses | — |
| **Read-Through** | Cache handles misses | — |
| **Write-Through** | — | Sync cache + DB |
| **Write-Behind** | — | Cache first, async DB |
| **Write-Around** | — | DB only; invalidate cache |

## What are cache replacement policies?

When cache is full, a **replacement policy** decides which entries to evict.

### Least Recently Used (LRU)

Evicts the item not accessed longest. Popular for general caching.

```csharp
// Cache capacity 3: [A, B, C]
// Access: A -> B -> D  =>  [A, B, D]  (C evicted)
```

### Most Recently Used (MRU)

Evicts the most recently accessed item — useful when recent access means temporary use.

```csharp
// Cache: [A, B, C]
// Access: B -> A -> D  =>  [A, C, D]  (B evicted)
```

### First-In, First-Out (FIFO)

Evicts oldest insertion regardless of access frequency.

```csharp
// Cache: [A, B, C], add D  =>  [B, C, D]  (A evicted)
```

### Least Frequently Used (LFU)

Evicts the least-accessed item. Effective when access patterns are skewed (CDNs).

```csharp
// Cache: [A(2), B(1), C(3)], add D  =>  [A(2), C(3), D]  (B evicted)
```

### Random Replacement (RR)

Evicts a random entry — minimal overhead, unpredictable patterns.

```csharp
// Cache: [A, B, C], add D  =>  random eviction (e.g., B)  =>  [A, C, D]
```

| Policy | Evicts | Best for |
|--------|--------|----------|
| **LRU** | Least recently used | General purpose |
| **MRU** | Most recently used | Temporary recent data |
| **FIFO** | Oldest insertion | Simple queue scenarios |
| **LFU** | Least frequently used | Skewed popularity |
| **RR** | Random | Low overhead, unpredictable access |

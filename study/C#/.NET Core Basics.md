## What is .NET Core?

**.NET Core** is an open-source, cross-platform framework by Microsoft for building modern, cloud-based, internet-connected applications. It is part of the larger .NET ecosystem and succeeded .NET Framework to address portability, modularity, and scalability limits.

**Key features:**

| Feature | Detail |
|---------|--------|
| Cross-platform | Runs on Windows, macOS, Linux |
| Performance | Lightweight, high-performance runtime |
| Modular | Include only needed packages; smaller footprint than full .NET Framework |
| Open source | Source on GitHub; community contributions |
| Unified model | C#, F#, VB.NET — web, mobile, desktop, cloud |
| Side-by-side versioning | Multiple versions on one machine without conflict |
| ASP.NET Core | Web/API framework within .NET Core — unified, high-performance |

In short, .NET Core is a versatile, modular platform for cross-platform development with improved performance over .NET Framework.

## What is .NET Standard?

**.NET Standard** is a specification defining APIs all .NET implementations must support (.NET Framework, .NET Core, Xamarin). The goal is portable, reusable libraries that work across platforms without modification.

- **API specification** — defines APIs every .NET implementation must provide
- **Portability** — a library targeting `netstandard2.0` runs on any platform supporting that version
- **Versioning** — incremental versions (1.0, 1.1, 2.0…); higher versions include all lower-version APIs
- **Compatibility** — no runtime itself; ensures a consistent API surface across runtimes

**Example — library usable in both .NET Core and .NET Framework:**

```bash
dotnet new classlib -n MyLibrary -f netstandard2.0
```

```csharp
using System;

namespace MyLibrary
{
    public class Greeter
    {
        public string Greet(string name)
        {
            return $"Hello, {name}!";
        }
    }
}
```

```bash
dotnet build
```

Reference from a .NET Core console app:

```bash
dotnet add reference ../MyLibrary/MyLibrary.csproj
```

```csharp
using MyLibrary;

class Program
{
    static void Main(string[] args)
    {
        var greeter = new Greeter();
        Console.WriteLine(greeter.Greet("World"));
    }
}
```

```bash
dotnet run
# Output: Hello, World!
```

**Evolution:** .NET 5+ unified the platform; .NET Standard remains relevant for older platform compatibility.

## What is the role of Program.cs file in ASP.NET Core?

In ASP.NET Core, `Program.cs` is fundamental to startup and configuration. It is the application entry point and host bootstrap.

| Role | Detail |
|------|--------|
| Entry point | Contains `Main` — where execution starts |
| Host building | Builds/configures the Host (runtime environment) |
| Configuration | Loads settings from appsettings, env vars, CLI args |
| Service configuration | Registers DI services via `ConfigureServices` |
| Request pipeline | Sets up middleware via `Configure` |

```csharp
using Microsoft.AspNetCore.Hosting;
using Microsoft.Extensions.Hosting;

namespace MyAspNetCoreApp
{
    public class Program
    {
        public static void Main(string[] args) =>
            CreateHostBuilder(args).Build().Run();

        public static IHostBuilder CreateHostBuilder(string[] args) =>
            Host.CreateDefaultBuilder(args)
                .ConfigureWebHostDefaults(webBuilder =>
                {
                    webBuilder.UseStartup<Startup>();
                });
    }
}
```

- **`Main`** — entry point; calls `CreateHostBuilder(args).Build().Run()`
- **`CreateHostBuilder`** — uses `Host.CreateDefaultBuilder` for default config (logging, settings); `ConfigureWebHostDefaults` configures Kestrel and points to the `Startup` class for services and middleware

## What is the role of ConfigureServices and Configure method?

Both methods are defined in the `Startup` class, referenced from `Program.cs`. They split service registration from middleware pipeline setup.

### ConfigureServices

**Role:** register services with the DI container so they can be injected into controllers, middleware, and other services.

- Registers MVC, EF Core, authentication, and custom application services
- Configures the DI container for dependency resolution

```csharp
public void ConfigureServices(IServiceCollection services)
{
    services.AddControllersWithViews();

    services.AddDbContext<MyDbContext>(options =>
        options.UseSqlServer(Configuration.GetConnectionString("DefaultConnection")));

    services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
        .AddCookie(options => { options.LoginPath = "/Account/Login"; });

    services.AddTransient<IMyService, MyService>();
}
```

### Configure

**Role:** define the HTTP request pipeline — the order middleware runs to process requests and responses.

- Sets up exception handling, static files, authentication, authorization, routing, and endpoints
- Middleware order matters: each component can short-circuit or pass to the next

```csharp
public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
{
    if (env.IsDevelopment())
        app.UseDeveloperExceptionPage();
    else
    {
        app.UseExceptionHandler("/Home/Error");
        app.UseHsts();
    }

    app.UseStaticFiles();
    app.UseAuthentication();
    app.UseAuthorization();
    app.UseRouting();
    app.UseEndpoints(endpoints =>
    {
        endpoints.MapControllerRoute(
            name: "default",
            pattern: "{controller=Home}/{action=Index}/{id?}");
    });
}
```

| Method | Purpose |
|--------|---------|
| `ConfigureServices` | DI registration — MVC, EF Core, auth, custom services |
| `Configure` | Middleware pipeline — exception handling, static files, routing, endpoints |

## What are the types of Service Lifetimes of an object/instance in ASP.NET?

In ASP.NET Core, services registered with DI have lifetimes that determine how and when instances are created and disposed. Choosing the wrong lifetime can cause bugs (shared mutable state) or performance issues (repeated expensive creation).

| Lifetime | Behavior | Use case | Registration |
|----------|----------|----------|--------------|
| **Transient** | New instance every request | Lightweight, stateless services | `AddTransient<T>()` |
| **Scoped** | One instance per request/scope | Per-request state (e.g., `DbContext`) | `AddScoped<T>()` |
| **Singleton** | One instance for app lifetime | Expensive creation, global cache/config | `AddSingleton<T>()` |

```csharp
services.AddTransient<IMyService, MyService>();
services.AddScoped<IMyService, MyService>();
services.AddSingleton<IMyService, MyService>();
```

**Choosing the right lifetime:**

- **Transient** — fresh instance every injection; ideal for stateless utilities
- **Scoped** — reuse within a single request; `DbContext` is the canonical example
- **Singleton** — one shared instance; use for configuration, caches, or thread-safe stateless services

## What is Request Delegate?

In ASP.NET Core, a **RequestDelegate** is a delegate type representing a method that handles HTTP requests within the middleware pipeline. It is central to building custom middleware.

```csharp
public delegate Task RequestDelegate(HttpContext context);
```

- Takes `HttpContext`, returns `Task` (supports async)
- Each middleware receives the **next** delegate and can run logic before/after calling it

```csharp
public class CustomMiddleware
{
    private readonly RequestDelegate _next;

    public CustomMiddleware(RequestDelegate next) => _next = next;

    public async Task InvokeAsync(HttpContext context)
    {
        await context.Response.WriteAsync("Custom Middleware: Before next\n");
        await _next(context);
        await context.Response.WriteAsync("Custom Middleware: After next\n");
    }
}
```

```csharp
public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
{
    app.UseMiddleware<CustomMiddleware>();
    app.UseRouting();
    app.UseEndpoints(endpoints => { endpoints.MapControllers(); });
}
```

- Constructor stores `_next` — the next middleware in the pipeline
- `InvokeAsync` runs custom logic, calls `_next(context)` to forward, then runs post-processing
- Returns `Task` so middleware can perform async I/O

**Summary:** RequestDelegate is the building block of the middleware pipeline — each component receives the next delegate and decides whether to call it.

## What is Run(), Use() and Map() method?

`Run()`, `Use()`, and `Map()` are `IApplicationBuilder` extension methods that configure how the request processing pipeline handles HTTP requests.

### Run()

Adds a **terminal** middleware delegate — does **not** call the next middleware; pipeline ends here unless a response is already sent.

```csharp
app.Run(async context =>
{
    await context.Response.WriteAsync("Hello from Run Middleware!");
});
```

No further middleware runs after `Run()`.

### Use()

Adds middleware that can handle the request directly **or** call `await next()` to pass control to the next component.

```csharp
app.Use(async (context, next) =>
{
    await context.Response.WriteAsync("Hello from first Use Middleware!\n");
    await next();
});
app.Use(async (context, next) =>
{
    await context.Response.WriteAsync("Hello from second Use Middleware!\n");
    await next();
});
```

Each `Use()` middleware writes output then forwards to the next.

### Map()

Branches the pipeline by request path. When the path matches, the sub-pipeline runs; otherwise it is skipped.

```csharp
app.Map("/admin", adminApp =>
{
    adminApp.Run(async context =>
        await context.Response.WriteAsync("Hello from Admin path!"));
});
app.Map("/user", userApp =>
{
    userApp.Run(async context =>
        await context.Response.WriteAsync("Hello from User path!"));
});
```

| Method | Behavior |
|--------|----------|
| `Run()` | Terminal — no next middleware |
| `Use()` | Calls `next()` to continue pipeline |
| `Map()` | Path-based branch/sub-pipeline |

## What are the types of Hosting in ASP.NET Core? What is In process and Out of process?

Hosting is how ASP.NET Core runs your application. Two main models exist when deploying behind IIS:

### In-Process Hosting

The application runs inside the IIS worker process (`w3wp.exe`) — same memory space as IIS.

- **Performance** — no inter-process communication; generally faster
- **Simplicity** — no separate reverse-proxy configuration needed
- **Trade-off** — less isolation; an app crash can affect the IIS worker process

Configure via `web.config` (IIS) or `UseIIS()` in `Program.cs`.

### Out-of-Process Hosting

The application runs in a separate process. IIS acts as a reverse proxy, forwarding requests to Kestrel.

- **Isolation** — app failures do not bring down IIS
- **Flexibility** — same pattern works with Nginx or Apache as reverse proxy
- **Trade-off** — slight overhead from IPC between IIS and Kestrel

Default when using Kestrel with IIS; configure via `web.config` reverse-proxy settings.

**Summary:** In-process is more efficient but less isolated; out-of-process trades slight overhead for isolation and deployment flexibility.

## What is Routing? Explain attribute routing in ASP.NET Core?

**Attribute routing** lets you define routes directly on controllers and actions using `[Route]` and HTTP method attributes. It is more flexible and explicit than conventional routing for APIs.

**1. Basic routing:**

```csharp
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet]
    public IActionResult GetAllProducts() { /* ... */ }

    [HttpGet("{id}")]
    public IActionResult GetProductById(int id) { /* ... */ }
}
```

- `api/products` → `GetAllProducts`; `api/products/5` → `GetProductById`

**2. Route parameters** — placeholders like `{id}` are bound to action method parameters

**3. Optional parameters** — `?` makes a segment optional; route matches with or without it

```csharp
[HttpGet("{category?}")]
public IActionResult GetProducts(string category) { /* ... */ }
```

**4. Route constraints:**

```csharp
[HttpGet("{id:int}")]
public IActionResult GetProduct(int id) { /* ... */ }

[HttpGet("price/{price:decimal}")]
public IActionResult GetProductsByPrice(decimal price) { /* ... */ }
```

- `{id:int}` — integer only; `{price:decimal}` — decimal only

**5. Route prefix on controller:**

```csharp
[Route("api/products")]
public class ProductsController : ControllerBase
{
    [HttpGet]
    public IActionResult GetAllProducts() { /* ... */ }

    [HttpGet("{id}")]
    public IActionResult GetProductById(int id) { /* ... */ }
}
```

**6. HTTP method attributes** — `[HttpGet]`, `[HttpPost]`, `[HttpPut]`, `[HttpDelete]`

```csharp
[Route("api/products")]
public class ProductsController : ControllerBase
{
    [HttpGet]  public IActionResult GetAllProducts() { /* ... */ }
    [HttpPost] public IActionResult CreateProduct([FromBody] Product product) { /* ... */ }
    [HttpPut("{id}")]  public IActionResult UpdateProduct(int id, [FromBody] Product product) { /* ... */ }
    [HttpDelete("{id}")] public IActionResult DeleteProduct(int id) { /* ... */ }
}
```

**7. Prefix + segment:**

```csharp
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet("search/{category}")]
    public IActionResult SearchProducts(string category) { /* ... */ }
}
```

**8. Route order** — routes match in definition order; place more specific routes (e.g., `{id}`) before general ones (bare `[HttpGet]`)

Attribute routing is especially useful for REST APIs where each action maps to a clear URL pattern.

## What are the techniques to save configuration settings in .NET Core?

Configuration settings manage application behavior and can be stored/accessed from multiple sources. ASP.NET Core's configuration system merges them with later sources overriding earlier ones.

| Technique | Detail |
|-----------|--------|
| **appsettings.json** | Primary JSON config file |
| **appsettings.{Environment}.json** | Environment overrides (Development, Production) |
| **secrets.json** | Dev secrets via `dotnet user-secrets` |
| **Environment variables** | `setx MY_SETTING "value"` (Win) / `export MY_SETTING="value"` (Linux/macOS) |
| **Command-line args** | `dotnet run --setting=value` |
| **User Secrets** | `dotnet user-secrets init` / `set "MySecret" "value"` — outside project, not in VCS |
| **Azure Key Vault** | Cloud secret store |
| **Custom providers** | Implement `IConfigurationProvider` + `IConfigurationSource` for DB/API sources |

**1. Configuration files** — `appsettings.json` is the primary store; environment-specific files override by environment name.

**2. Environment variables** — ideal for secrets and deployment-specific values; automatically loaded by `CreateDefaultBuilder`.

**3. Command-line arguments** — override settings at runtime via `ConfigureAppConfiguration` + `AddCommandLine`.

**4. User Secrets** — development-only; stored outside the project directory, excluded from source control.

**5. Azure Key Vault** — production secrets in the cloud; integrate via `AddAzureKeyVault`.

**6. Custom providers** — pull settings from databases, remote APIs, or any custom source.

```json
{
  "AppSettings": {
    "SiteTitle": "My App",
    "MaxItems": 100
  }
}
```

```csharp
var mySetting = Environment.GetEnvironmentVariable("MY_SETTING");
```

```csharp
public static IHostBuilder CreateHostBuilder(string[] args) =>
    Host.CreateDefaultBuilder(args)
        .ConfigureAppConfiguration((context, config) =>
        {
            config.AddCommandLine(args);
        })
        .ConfigureWebHostDefaults(webBuilder =>
        {
            webBuilder.UseStartup<Startup>();
        });
```

```csharp
public void ConfigureServices(IServiceCollection services)
{
    var keyVaultEndpoint = new Uri(Environment.GetEnvironmentVariable("KEY_VAULT_ENDPOINT"));
    var builder = new ConfigurationBuilder()
        .AddAzureKeyVault(keyVaultEndpoint, new DefaultAzureCredential());
    Configuration = builder.Build();
    services.AddSingleton<IConfiguration>(Configuration);
}
```

**Accessing via DI:**

```csharp
public class MyService
{
    private readonly IConfiguration _configuration;

    public MyService(IConfiguration configuration) => _configuration = configuration;

    public void PrintSettings()
    {
        var siteTitle = _configuration["AppSettings:SiteTitle"];
        Console.WriteLine($"Site Title: {siteTitle}");
    }
}
```

## What is CORS? Why CORS restriction is required? How to fix CORS error?

**CORS** (Cross-Origin Resource Sharing) is a browser security feature that controls how resources on one domain can be requested from another. Servers specify who may access their resources and how.

**Why CORS restriction is required:**

- **Prevent unauthorized access** — without CORS, a malicious site could make requests to another domain's APIs and potentially read sensitive data
- **Protect user data** — ensures only trusted origins can interact with server resources; mitigates CSRF-style attacks
- **Server control** — servers explicitly declare allowed origins, headers, and methods

**How to fix CORS errors:** configure the server to return the correct CORS response headers. In ASP.NET Core:

```csharp
public void ConfigureServices(IServiceCollection services)
{
    services.AddCors(options =>
    {
        options.AddPolicy("AllowSpecificOrigin", builder =>
        {
            builder.WithOrigins("https://example.com")
                .AllowAnyHeader()
                .AllowAnyMethod();
        });
    });
    services.AddControllers();
}
```

```csharp
public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
{
    if (env.IsDevelopment())
        app.UseDeveloperExceptionPage();
    else
    {
        app.UseExceptionHandler("/Home/Error");
        app.UseHsts();
    }

    app.UseHttpsRedirection();
    app.UseStaticFiles();
    app.UseRouting();
    app.UseCors("AllowSpecificOrigin");
    app.UseAuthorization();
    app.UseEndpoints(endpoints => { endpoints.MapControllers(); });
}
```

- `WithOrigins("https://example.com")` — allowed domains
- `AllowAnyHeader()` / `AllowAnyMethod()` — permit any request headers and HTTP verbs
- Apply policy with `app.UseCors("AllowSpecificOrigin")` **after** `UseRouting()` and **before** `UseAuthorization()`

CORS errors appear in the browser console when the server's response lacks the expected `Access-Control-*` headers for the requesting origin.

## What is In-Memory caching & Distributed Caching? When to use what?

**Caching** stores frequently accessed data in temporary storage for faster retrieval and reduced load on the primary data source. .NET Core supports in-memory and distributed caching.

### In-Memory Caching

Stores data in the application server's process memory — fast but local to that instance.

| Aspect | Detail |
|--------|--------|
| Scope | Local to one app instance |
| Speed | Very fast (RAM) |
| Lifetime | Lost on restart; not shared across instances |

**Use when:** single-instance apps, short-lived data (sessions, configs), dev/test.

### Distributed Caching

Stores data in a separate cache service (Redis, SQL Server, NCache) shared across multiple application instances.

| Aspect | Detail |
|--------|--------|
| Scope | Shared across instances |
| Scalability | Scale-out friendly |
| Persistence | Some providers survive restarts |

**Use when:** multi-instance deploys, high availability, large/shared datasets.

**Providers:** Redis, SQL Server, NCache.

### Related: Session & State Management

HTTP is stateless — maintaining state between requests requires explicit session management. Three main approaches in ASP.NET Core:

| Mechanism | Detail |
|-----------|--------|
| **Session Middleware** | Built-in middleware; stores session ID in a cookie (default `.AspNetCore.Session`) and data server-side |
| **In-Memory Session** | Session data in server process — suitable for small single-server apps; data lost on restart |
| **Distributed Session** | Session in Redis/SQL Server — required for server farms and cloud scale-out |
| **ViewData/ViewBag** | Pass data controller → view for the current request only |
| **TempData** | Dictionary surviving to the **next** request — commonly used across redirects |

### JWT Token

JWTs (JSON Web Tokens) are used in authentication: user logs in, receives a JWT, and sends it with each subsequent request. The server verifies the token to confirm identity and permissions.

### SAML Workflow

**SAML** (Security Assertion Markup Language) is an XML-based standard for exchanging authentication and authorization data between an Identity Provider (IdP) and a Service Provider (SP).

1. **User accesses SP** — attempts to log in or reach a protected resource
2. **SP redirects to IdP** — user is not yet authenticated; browser sent to IdP login

```http
GET /saml/login HTTP/1.1
Host: identity-provider.com
```

3. **User authenticates at IdP** — enters credentials; IdP verifies and authenticates
4. **IdP generates SAML assertion** — XML document with user identity and authentication status

```http
POST /saml/acs HTTP/1.1
Host: identity-provider.com
Content-Type: application/x-www-form-urlencoded

SAMLResponse=<base64-encoded-SAML-assertion>
```

5. **Assertion delivered to browser** — IdP returns assertion via form POST to the user's browser

```html
HTTP/1.1 200 OK
Content-Type: text/html

<form action="https://service-provider.com/saml/acs" method="post">
  <input type="hidden" name="SAMLResponse" value="<base64-encoded-SAML-assertion>" />
  <button type="submit">Submit</button>
</form>
```

6. **Browser submits assertion to SP** — auto-POST to the SP's Assertion Consumer Service (ACS) endpoint

```http
POST /saml/acs HTTP/1.1
Host: service-provider.com
Content-Type: application/x-www-form-urlencoded

SAMLResponse=<base64-encoded-SAML-assertion>
```

7. **Signature verification** — SP verifies the digital signature on the assertion using the IdP's public key to confirm it was not tampered with and was issued by a trusted IdP. On failure, access is denied. On success, SP extracts user identity/attributes and grants access. The signature is added to `<saml:Assertion>` by the IdP using its private key.

8. **SAML session workflow** — unlike OAuth/OIDC, the SAML assertion is **not** sent on every subsequent request. It is used only during initial authentication to establish a session. The SP then issues a session cookie or token for ongoing requests.

9. **Session establishment** — assertion establishes the user session at the SP
10. **Session management** — subsequent requests use the SP-issued session cookie/token in HTTP headers; no repeated SAML assertion

### Cryptography

| Type | Detail |
|------|--------|
| **Symmetric** | Single shared secret key for both encrypt and decrypt — AES, DES, 3DES |
| **Asymmetric** | Public/private key pair — RSA, ECC, DSA |

**Asymmetric encryption/decryption:**

- **Encrypt with public key** — anyone can encrypt; only the holder of the private key can decrypt
- **Decrypt with private key** — private key must remain confidential

**Asymmetric signing/verification:**

- **Sign with private key** — entity generates a digital signature over the data
- **Verify with public key** — anyone with the public key can confirm authenticity and integrity

### SSL/TLS

SSL/TLS combines asymmetric and symmetric cryptography for secure client-server communication.

**Handshake phase:**

1. **Server authentication** — client connects; server sends digital certificate (public key + identity)
2. **Certificate validation** — client checks validity, signature, and trusted CA
3. **Key exchange** — client generates a symmetric session key, encrypts it with the server's public key, sends to server
4. **Session key agreement** — server decrypts with its private key; both sides now share a session key

**Data transfer phase:**

- Data encrypted/decrypted symmetrically (e.g., AES) using the shared session key
- Protects against eavesdropping and tampering

**Termination phase:**

- Connection closed gracefully; session key discarded for forward secrecy
- Each client-server session gets its own unique session key during handshake
